Equipment reference

Enchantments.

Pixel's enchantment system is built around equipment families, stable enchant identity and a shared combat model. This guide documents what the mechanics actually do rather than inferring behavior from their names.

Current source audited— public catalogue entriesRetired identities stay retired
01 / System contract

Compatibility is deliberate, not accidental.

Equipment families own their allowed pool, while combat effects follow the same damage and mitigation rules instead of creating separate interpretations of a hit.

—
Global enchant cap per item

The cap applies across the equipment model. A family can expose characteristic and shared enchantments, but an item cannot accumulate an unbounded list simply because several systems recognize it.

02 / Equipment families

One enchant system, several mechanical identities.

Sword, Axe and Spear are distinct melee families. Bow, Elytra and Shield preserve their own rules instead of inheriting whatever happens to fit a sword.

03 / Specialized mechanics

Some enchants alter combat semantics, not just damage.

These mechanics have dedicated behavior and are documented according to that behavior instead of being reduced to a generic damage proc.

04 / Name vs behavior

Names do not grant mechanics that are not defined.

A reliable reference describes verified behavior instead of filling semantic gaps with genre assumptions.

Why this matters

For example, a name that sounds like fire, frost, momentum or disruption is not documentation for a damage-over-time, slow, movement or crowd-control mechanic. Those behaviors only become part of the guide when current evidence supports them.

05 / Retired identities

Retirement is part of the compatibility contract.

Removing an active mechanic does not make its identity available for an unrelated effect. Historical identities stay classified so older items and references cannot silently acquire a different meaning later.

06 / Documentation confidence

Source confidence is explicit.

Current family rules, specialized effects, conservative semantics and retired identities are source-verified. That evidence supports this reference, but it does not substitute for a live-client pass that has not been performed.

Legacy names and old documentation are not current behavior.

An enchant appearing in the old GitBook or another stale reference does not make it part of the current catalogue again.
